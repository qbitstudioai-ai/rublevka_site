# Развёртывание Rublevka Staging

Временная площадка работает по адресу `https://rublevka.allqbit.ru`. Приложения собираются из явно указанного коммита GitHub. Конфигурация развёртывания хранится в `deploy/staging/`. Рабочая площадка `rublevka34.com` и отдельная афиша `meropriyatiya.allqbit.ru` обслуживаются независимо.

## Устройство

| Компонент | Размещение |
| --- | --- |
| Основной Next.js | Контейнер `rublevka-staging-site-1`. Единственный контейнер проекта на сети действующего прокси. |
| Афиша `events-original` | `rublevka-staging-events-1`. Основной сайт переписывает `/meropriyatiya/*` на внутреннее имя `events:3000`. |
| PostgreSQL | `rublevka-staging-db-1`. Данные CMS, технические таблицы ассистента и отдельная схема `rublevka_n8n`. |
| SQLite | Постоянный файл афиши. Снимки выполняются через SQLite Backup API. |
| HTTPS | Действующий Caddy обслуживает отдельный блок staging и автоматически выпускает и продлевает сертификат. |

У базы и афиши собственная внутренняя сеть Docker. Контейнеры проекта не публикуют порты на хост. Caddy обращается к основному контейнеру на существующей сети прокси, а основной сайт обращается к базе и афише на закрытой сети. Каталоги данных монтируются с хоста, поэтому чистка неиспользуемых Docker volumes их не удаляет.

| Путь | Назначение |
| --- | --- |
| `/opt/rublevka-staging/releases/<commit>` | Исходный код конкретной сборки из контролируемого архива Git. |
| `/opt/rublevka-staging/current` и `current-commit` | Ссылка на архив текущей версии и её точный SHA. |
| `/opt/rublevka-staging-data` | PostgreSQL, SQLite, загруженные CMS-медиа и медиа афиши. |
| `/opt/rublevka-staging-config` | Compose, эксплуатационные команды, настройки и секреты. Доступ только оператору сервера. |
| `/opt/rublevka-staging-backups` | Локальные резервные копии и контрольные суммы. |

Публичный браузерный доступ защищён HTTP Basic Auth. `robots.txt` доступен без входа. Caddy выставляет `X-Robots-Tag`, а приложение собирается с `SEO_INDEXING_ENABLED=false`. Авторизованные серверные маршруты ассистента используют свои ключи и подписи. Внутренний SQLite API закрыт на внешнем прокси. Данные доступа к staging и двум административным панелям лежат в `reviewer-access` на сервере. Получать их нужно отдельным защищённым каналом.

## Первый запуск

1. Подготовить DNS A для staging-домена и убедиться в доступности портов 80 и 443 действующего Caddy. Установить файлы из `deploy/staging/` в закрытый каталог конфигурации. Предоставленный `03_setup.sql` скопировать туда отдельно с правами `0600`.
2. Запустить `bootstrap.sh ДОМЕН ПОЛНЫЙ_СОГЛАСОВАННЫЙ_SHA ПУТЬ_К_03_setup.sql`. Команда создаёт секреты, изолированную PostgreSQL и роли, применяет SQL и Drizzle, устанавливает опубликованный контент из репозитория и создаёт администратора. Начальный каталог SQLite наполняется из `events-original/db/public-catalog.json`.
3. Выполнить `configure-proxy.sh`. Скрипт пробует конфигурацию Caddy до reload, меняет только блок staging и откатывает перезагрузку при ошибке. Проверить HTTPS и переадресацию HTTP. Установить и включить `rublevka-staging-backup.timer` с одноимённым service из комплекта.
4. Выполнить `smoke.sh`, ручную проверку за Basic Auth и первую проверку восстановления.

Разрешённый для этой установки контент берётся из утверждённого коммита. Данные действующей афиши и локальные SQLite, учётные записи, платежи, registrations и секреты в архив не включаются. Отдельный перенос опубликованных редакций и загрузок CMS требует проверенного экспортного набора. Для SQLite дополняющий перенос выполняется через согласованный snapshot и проверку содержимого, включая принадлежность файлов.

## Обновление и откат

Разработка, проверки и публикация идут локально. Руководитель утверждает полный SHA, после чего оператор запускает на сервере:

```bash
/opt/rublevka-staging-config/release.sh СОГЛАСОВАННЫЙ_ПОЛНЫЙ_SHA
/opt/rublevka-staging-config/smoke.sh
```

Скрипт проверяет наличие коммита на GitHub и собирает оба образа до переключения. Для новой версии сохраняет резервную копию действующей, применяет миграции и выполняет проверку маршрутов и API. Инициализация контента выполняется только при первом запуске. Права приложения после миграции ограничиваются таблицами CMS и ассистента. Исходники на сервере не редактируются. Падение сборки оставляет старые контейнеры в работе. Если проверка после переключения не прошла, скрипт пробует поднять сохранённые предыдущие образы. Если они недоступны, оператор запускает release.sh с предыдущим SHA.

Для отката, совместимого со схемой данных, разверните точный предыдущий SHA тем же скриптом. Проверьте совместимость миграций до запуска. Для несовместимой миграции запланируйте паузу записи до предрелизного снимка и отдельное окно восстановления. Обычный backup снимает базы и медиа последовательно, поэтому при конкурентной записи снимок может потребовать проверки ссылок. В этом случае записи после создания снимка требуют отдельного решения о переносе. План чистки Docker на узле может удалить неиспользуемые образы. Скрипт умеет пересобрать предыдущую версию из GitHub.

Домен задаётся через `SITE_URL` и `APP_URL`, причём `APP_URL` содержит origin без `/meropriyatiya`. Укажите новый домен в конфигурации, пересоберите текущий согласованный SHA через `release.sh` и примените новый блок Caddy через `configure-proxy.sh`. Проверьте HTTPS, canonical и ссылки афиши.

## Резервное копирование и восстановление

`rublevka-staging-backup.timer` запускает ежедневный backup в 04:20 по часам сервера с задержкой до двух минут. `backup.sh` сохраняет дамп PostgreSQL и роли, SQLite snapshot, медиа, закрытую конфигурацию и SHA релиза. Снимок получает контрольные суммы. Локальные копии старше 14 дней очищаются автоматически. Статус смотрят в журнале `rublevka-staging-backup.service`. Защищённая копия вне этого узла требует отдельного получателя и его политики хранения.

```bash
/opt/rublevka-staging-config/backup.sh
/opt/rublevka-staging-config/verify-backup.sh /opt/rublevka-staging-backups/КАТАЛОГ_СНИМКА
systemctl list-timers rublevka-staging-backup.timer
journalctl -u rublevka-staging-backup.service -n 30
```

Проверка загружает дамп во временную отдельную базу, сверяет контрольные суммы, проверяет SQLite и ищет в архиве загруженные файлы, на которые ссылаются снимки баз. Для рабочего восстановления сначала проверьте снимок, затем остановите только контейнеры сайта и афиши. Заархивируйте текущее состояние до изменений. На новом узле создайте изолированный экземпляр PostgreSQL с ролью `rublevka_bootstrap`. При импорте `postgres-roles.sql` пропустите только `CREATE ROLE rublevka_bootstrap;`, существующие роли базы никого другого не должны затрагиваться. Восстановите дамп в новый экземпляр с `pg_restore --create --exit-on-error -d postgres`, чтобы восстановить имя базы, владельца и права CONNECT. На существующем узле лучше сначала импортировать в отдельную пустую базу, проверить её и выполнить контролируемое переключение. Извлеките архив медиа и конфигурации с числовыми UID/GID, восстановите секреты с исходными правами и проверьте доступ записи контейнерного UID 1000 к медиа. Восстановите SQLite в пустой каталог афиши без прежних WAL/SHM-файлов. Поставьте отметки инициализации CMS и SQLite, затем соберите SHA из файла `commit`, поднимите контейнеры и запустите `smoke.sh`.

## Окружение и доступ n8n

| Настройки | Где хранятся |
| --- | --- |
| `SITE_URL`, `SEO_INDEXING_ENABLED`, `CMS_ENABLED`, `CMS_MEDIA_DIR`, `DATABASE_URL`, `SITE_ADMIN_SESSION_SECRET`, `EVENTS_ORIGINAL_ORIGIN` | `site.env` |
| `APP_URL`, `EVENTS_ASSISTANT_MOUNTED`, `ASSISTANT_EVENTS_KEY`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `ADMIN_SESSION_SECRET` | `events.env` |
| `ASSISTANT_CHAT_ENABLED`, `ASSISTANT_KNOWLEDGE_KEY`, `ASSISTANT_EVENTS_KEY`, `ASSISTANT_N8N_WEBHOOK_URL`, `ASSISTANT_N8N_WEBHOOK_KEY`, `ASSISTANT_N8N_CALLBACK_KEY`, `ASSISTANT_OPERATOR_KEY`, `ASSISTANT_RETENTION_HOURS` | `site.env` |
| Учётные данные миграций, bootstrap и роли workflow | Раздельные файлы `migration.env`, `postgres.env`, `n8n-db.env`. |

Основной сайт имеет права на необходимые операции с таблицами CMS и ассистента. Миграции выполняет отдельный владелец БД. Роль `rublevka_n8n` имеет доступ к схеме workflow и не имеет доступа к прикладной схеме. Отдельный сервер n8n сначала подключите к API по HTTPS согласно [контракту ассистента](ASSISTANT_API.md). Для SQL предложен отдельный SSH-туннель с ограниченным пользователем без shell и пересылкой только на PostgreSQL staging либо приватный VPN. Для туннеля потребуется отдельно настроить стабильный loopback-прокси на изолированную БД. Внешний порт 5432 для этого не нужен. Интеграция остаётся выключенной до проверки руководителем. Подлинные уведомления и платежи в staging не используются.

См. [протокол проверки ассистента](ASSISTANT_API.md) и [документацию модуля афиши](../events-original/DEPLOYMENT.md).
