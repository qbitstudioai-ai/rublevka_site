# Архитектура проекта «Рублевка»

## 1. Цели и ограничения

Проект строится как модульный монолит: одно приложение Next.js и один процесс поставки, внутри которого домены имеют явные границы. Это быстрее и надёжнее для текущего масштаба, чем микросервисы или monorepo, и не мешает позднее вынести модуль при подтверждённой нагрузке или организационной необходимости.

Сейчас реализован только минимальный публичный каркас. Финальная главная страница, навигация, бронирование, авторизация, чат, админка и база данных намеренно не реализованы.

## 2. Технологический фундамент

| Компонент | Выбор | Причина |
| --- | --- | --- |
| Web-фреймворк | Next.js 16.4.6, App Router | Server Components, SSR/SSG, Metadata API, route handlers и встроенная оптимизация изображений дают SEO-фундамент без отдельного frontend/backend-приложения. |
| UI | React 19.3.1 | Стабильная версия, совместимая с выбранным Next.js; интерактивность можно подключать локально, сохраняя страницы серверными по умолчанию. |
| Язык | TypeScript 5.9.3, `strict` | Раннее обнаружение ошибок и проверяемые контракты доменов и интеграций; выбрана актуальная линия, поддерживаемая lint/tooling-стеком Next.js. |
| Стили | нативный CSS, cascade layers и design tokens | Нулевой runtime, прозрачная каскадность и отсутствие преждевременной зависимости от UI-фреймворка. |
| Качество | ESLint 9.39.3 + `eslint-config-next` | Проверки React, TypeScript, доступности и Core Web Vitals в единой конфигурации без неподдерживаемых peer overrides. |
| Данные (следующий этап) | PostgreSQL | Транзакции, связи и зрелая экосистема подходят для контента, заявок, событий и ролей. БД пока не подключена. |

Node.js 20.9+ — минимальное требование Next.js; для CI и production следует зафиксировать актуальную LTS-линию. Текущие версии сверены 18 ноября 2026 года по официальным релизам и npm.

### Зависимости сейчас

Production-зависимости ограничены `next`, `react` и `react-dom`. Инструменты разработки — TypeScript, ESLint, конфигурация Next.js и типы. Это весь набор, необходимый для запуска и проверки каркаса.

### Зависимости только при появлении сценария

- драйвер PostgreSQL и миграции/ORM — после утверждения модели контента и инфраструктуры;
- библиотека валидации — вместе с первой серверной формой или внешним контрактом;
- аутентификация — перед админкой, после выбора поставщика и модели ролей;
- хранилище файлов, очередь и rate limiting — только при измеримой потребности;
- 3D/animation-библиотеки — точечно после дизайн-прототипа и performance budget;
- тестовый browser runner — с первым интерактивным пользовательским сценарием.

## 3. Физическая структура

```text
src/
├── app/
│   ├── (public)/page.tsx     # публичная индексируемая часть
│   ├── globals.css           # reset, токены и базовые стили
│   ├── layout.tsx            # корневые метаданные и язык
│   ├── robots.ts             # robots.txt
│   └── sitemap.ts            # sitemap.xml
├── components/
│   └── ui/                   # переиспользуемые примитивы интерфейса
└── server/
    └── site-url.ts           # серверная конфигурация origin/canonical
```

Будущая админка получит route group `src/app/(admin)/admin` только с первым рабочим административным сценарием. Серверные домены появятся в `src/server/modules/<domain>`, интеграции — в `src/server/integrations/<provider>`. Route handlers остаются тонким транспортным слоем: авторизация, разбор запроса и вызов use case.

## 4. Границы модулей

| Модуль | Ответственность | Взаимодействие |
| --- | --- | --- |
| Public web | Каталоги проживания, беседок, залов, бани, ресторана и услуг; страницы контактов и предложений | Читает опубликованный контент; вызывает прикладные сценарии заявок и внешнего бронирования. |
| Content & SEO | Страницы, медиа, метаданные, redirects, публикация и sitemap | Отдаёт публичной части только опубликованные версии; позже управляется через админку. |
| Map | Координаты объектов, слои и точки интереса | Получает публичные данные объектов; тяжёлая карта загружается только после взаимодействия или в видимой области. |
| Accommodation booking | Переход/виджет TravelLine и, если разрешено, поиск доступности | Работает только через адаптер TravelLine; не хранит независимый inventory или статус брони. |
| Events | Афиша, лимиты мест и регистрация гостей | Использует собственную модель событий и регистраций; уведомляет администрацию через модуль notifications. |
| Banquet leads | Заявки на свадьбы, банкеты и корпоративы | Не смешивается с бронями проживания; передаёт статус в админку и уведомления. |
| Conversations | Диалоги с администрацией и передача оператору | Единый доменный интерфейс для web-чата и будущего бота; каналы — отдельные адаптеры. |
| Notifications | Системные email/Telegram-уведомления | Получает доменные события, не владеет бизнес-статусами заявок. |
| Admin & access | Управление контентом, событиями, заявками и ролями | Серверная авторизация на каждом use case; UI не является границей безопасности. |
| Guest account (позже) | Профиль и история разрешённых гостю действий | Не дублирует TravelLine и включается только после согласования идентификации гостя. |

Модули взаимодействуют через типизированные прикладные интерфейсы внутри процесса. Доменные события допустимы для слабосвязанных побочных эффектов (например, уведомления), но отдельный брокер сообщений сейчас не нужен.

## 5. Данные и PostgreSQL

PostgreSQL станет источником истины для собственного контента, событий, регистраций, банкетных заявок, диалогов, ролей и аудита. Данные проживания, доступность, тарифы и статусы броней остаются под управлением TravelLine. Локально можно хранить только технические ссылки, кеш разрешённых публичных данных и журнал синхронизации с понятным TTL/источником.

Персональные данные минимизируются по назначению, имеют сроки хранения и не попадают в логи. Для административных действий необходим audit trail. Схема и миграции проектируются вместе с первым сохраняемым сценарием, а не заранее.

## 6. TravelLine

Интеграция оформляется серверным адаптером `src/server/integrations/travelline`. Доменные модули не должны импортировать SDK или HTTP-форматы TravelLine напрямую.

### Возможные режимы

1. **TL: Booking Engine / переход в модуль бронирования.** Предпочтительный первый вариант: TravelLine сохраняет весь checkout, оплату и бронь. Конкретный способ встраивания и параметры подтверждаются в текущем кабинете объекта и у поддержки TravelLine.
2. **Search API.** После выдачи прав можно показывать актуальные варианты/минимальную цену, а завершение бронирования оставлять в Booking Engine.
3. **Content API.** Может быть источником сведений о категориях, тарифах, услугах и фото, если владелец контента и правила синхронизации утверждены.
4. **Read Reservation API.** Только для разрешённых административных сценариев; не повод создавать параллельный booking ledger.
5. **Вебхуки.** Принимающий HTTPS endpoint проверяет аутентификацию, идемпотентность по `eventId`, быстро отвечает `200`, а актуальное состояние дочитывает через разрешённый API. Состав событий зависит от подключённых компонентов TravelLine.

Partner API использует OAuth 2.0 Client Credentials (`client_id`/`client_secret`), выдаёт короткоживущий access token и имеет лимиты запросов. Секреты хранятся только на сервере; токен кешируется до истечения с запасом. На текущем этапе ключи и реальные вызовы не нужны.

Перед реализацией требуется подтвердить у владельца объекта: активные продукты TravelLine, `propertyId`, доступные API/scopes, формат Booking Engine, нужные webhooks, тестовую среду и правила обработки персональных данных.

## 7. SEO и производительность

- Каждая основная услуга получает отдельный понятный URL, один смысловой `h1`, уникальные `title`/`description` и canonical.
- App Router рендерит содержимое на сервере; статические данные генерируются заранее, изменяемые — через контролируемую revalidation.
- `robots.ts` и `sitemap.ts` уже входят в каркас. Sitemap расширяется опубликованными URL из content-модуля.
- Schema.org добавляется только при наличии подтверждённых фактов. Для комплекса вероятны `LodgingBusiness`, `Restaurant`, `Event` и `Offer`, но типы и поля утверждаются по реальным данным.
- Региональные страницы отвечают намерению пользователя для Волгограда и Волгоградской области; ключевые слова не размножаются механически.
- Реальные фото обрабатываются через `next/image`: явные размеры, responsive `sizes`, современные форматы и приоритет только для LCP-изображения.
- 3D, карта, галереи и чат — ленивые клиентские островки. Основной текст и навигация не зависят от JavaScript.
- Performance budget перед визуальным этапом: контролировать LCP/INP/CLS, объём клиентского JS и вес первого экрана на среднем мобильном устройстве.
- Любая анимация учитывает `prefers-reduced-motion`; на слабых устройствах допускается статическая композиция без потери содержания.

## 8. Безопасность и эксплуатация

- Переменные окружения валидируются на старте; `.env*` исключены из Git, кроме безопасного `.env.example`.
- Входные данные проверяются на сервере. Для форм нужны CSRF/origin-проверки, rate limiting, anti-spam и безопасная обработка файлов.
- Админские route handlers проверяют сессию и право на действие, а не только принадлежность к route group.
- Внешние вызовы имеют timeout, ограниченные retry с jitter и структурированные ошибки без секретов/PII.
- Логи, метрики и tracing добавляются вместе с backend-сценариями. Для TravelLine отдельно измеряются latency, rate-limit и ошибки синхронизации.

## 9. Этапы развития

1. Утвердить карту страниц, контент-модель, дизайн-направление и факты об объекте.
2. Реализовать публичные каталоги и страницы услуг на статическом/управляемом контенте.
3. Подключить PostgreSQL и минимальную админку публикации контента с ролями.
4. Согласовать и внедрить TravelLine сначала через Booking Engine, затем при необходимости через разрешённые API/webhooks.
5. Добавить события и регистрации, затем банкетные заявки и уведомления.
6. Добавить карту, чат и бот после проверки базовых конверсий и производительности.
7. Проектировать личный кабинет только после согласования идентификации и источников данных.

## 10. Зафиксированные решения и открытые вопросы

Зафиксировано: модульный монолит, App Router, server-first rendering, строгий TypeScript, PostgreSQL в перспективе, адаптеры для внешних систем, TravelLine как источник истины бронирований проживания.

Требуют решения руководителя:

- окончательная информационная архитектура, шапка и меню;
- фактический адрес/география, перечень объектов, цены, контакты и юридические реквизиты;
- CMS-подход и роли редакторов;
- провайдер размещения, CI/CD и preview-окружения;
- доступные продукты и права TravelLine;
- правила обработки персональных данных, сроки хранения и тексты согласий;
- канал администраторского чата и бот;
- пределы визуальных эффектов и performance budget после прототипа.
