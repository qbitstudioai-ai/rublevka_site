# Состояние проекта

## Цель продукта

Веб-приложение для регистрации участников мероприятий загородного комплекса «Рублёвка». Интерфейс — фирменная анкета регистрации участника с возможностью дополнительно выбрать активности и услуги. Он сохраняет стиль, фотографии и тон бренда, но назначение страницы (регистрация) должно быть очевидно сразу.

## Принятые решения

- Подход к интерфейсу: mobile-first, короткий сценарий, progressive disclosure, один главный CTA на смысловой экран.
- Визуальная основа берётся с действующего сайта [rublevka34.com](https://rublevka34.com/), но его HTML и недостатки адаптивности не копируются.
- Канонические UI-правила — в `DESIGN_SYSTEM.md` и project-level skill `.claude/skills/rublevka-ui-design/SKILL.md`. Публичный UI v2 принят как базовый.
- Стек: Next.js 16 (App Router, TypeScript), SQLite (`better-sqlite3`), `zod`, `sharp`. Внешних сервисов и ORM нет. Подробнее — `ARCHITECTURE.md` и `DATABASE.md`.

## Текущий этап

Главная страница — список мероприятий: вместо перенаправления на ближайшее мероприятие `/` показывает все опубликованные мероприятия с датой от сегодняшней, ближайшие первыми. Карточка ведёт на `/event/[slug]`; список сразу отражает публикацию, архив и удаление в админке. Это постоянный адрес для ссылки «Мероприятия» с основного сайта rublevka34.com (подключение к основному сайту — следующий шаг).

Регистрация на прошедшее мероприятие закрыта: по ссылке — экран «Мероприятие уже прошло», сервер отклоняет такие регистрации. В e2e демо-мероприятие сдвигается на неделю вперёд от даты запуска (`scripts/e2e-prepare.mjs`), чтобы тесты не зависели от календаря.

Способы оплаты: в админпанели выбирается, что показать участнику — QR-код (загружается фото или скриншот), перевод по номеру телефона (с именем получателя и кнопкой «Скопировать номер») или оба способа (миграция `004`).

Этап 6 «Подготовка к production» завершён (реальное развёртывание не выполнялось):

- Telegram-уведомления доставляются через durable outbox в SQLite: запись создаётся в транзакции регистрации, повтор — `npm run telegram:retry` (cron) и кнопка «Повторить неотправленные» в админке;
- резервные копии `npm run backup`: SQLite через online backup API + uploads в одном `.tar.gz`, retention по `BACKUP_RETENTION_DAYS`; восстановление — `RESTORE.md`;
- `/api/health` (SQLite, миграции, uploads) без секретов и путей;
- проверка production-окружения при запуске; корректное закрытие SQLite при остановке;
- standalone-сборка Next.js, `Dockerfile`, `docker-compose.production.yml`, smoke-скрипт образа; требования к reverse proxy и volume — `DEPLOYMENT.md`;
- ограничение частоты учитывает IP только при `TRUST_PROXY=true`.

Этап 5 «Уведомления и выгрузка» завершён ранее:

- обязательны только ФИО и телефон; мессенджер необязателен и хранится как `NULL` (миграция `002`);
- после каждой регистрации администрация получает сообщение в Telegram напрямую через Bot API (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`); сбой Telegram не отменяет регистрацию;
- в `/admin/settings` показан статус Telegram и есть кнопка «Отправить тестовое уведомление»;
- на странице мероприятия кнопка «Скачать Excel» выгружает всех участников в `.xlsx` с колонками «Услуга 1…N» из snapshots;
- настройка бота описана в `TELEGRAM.md`.

Этап 4 «Работающее приложение» завершён ранее:

- SQLite хранит мероприятия, услуги, галереи, регистрации со snapshots и общие настройки; схема управляется SQL-миграциями (`npm run db:migrate`), демо-данные — `npm run db:seed`;
- у каждого мероприятия своя ссылка `/event/[slug]`; черновики и архив публично отдают 404;
- кнопка «Зарегистрироваться» создаёт запись: сервер валидирует данные, проверяет услуги, сам считает итог и в одной транзакции сохраняет регистрацию и snapshots;
- после регистрации показывается «Регистрация завершена»; при сумме больше 0 ₽ появляется «Оплатить выбранные услуги» → `/payment/[publicId]`;
- страница оплаты читает сумму, ФИО и услуги из сохранённой регистрации; ФИО и сумма больше не передаются в адресе;
- защищённая админпанель `/admin` (единственный администратор, данные входа в env): мероприятия, услуги, загрузка фото и QR, регистрации с поиском, общие настройки, архив и очистка данных;
- загруженные изображения хранятся в `UPLOADS_DIR`, оптимизируются и удаляются, когда на них больше нет ссылок;
- инструкция владельцу — `ADMIN_GUIDE.md`.

## Зафиксированные решения по оплате и настройкам

- **QR оплаты единый** для всех мероприятий, услуг и участников (`app_settings.payment_qr_image`).
- **Реальной платёжной системы нет.** Сервис не узнаёт о факте оплаты.
- Пользователь **самостоятельно вводит сумму** в банковском приложении; сумма берётся из сохранённой регистрации.
- **Участие может быть платным** (миграция `007`): стоимость задаётся у мероприятия, обязательна при регистрации, входит в итог вместе с услугами и фиксируется в регистрации; пусто — бесплатно.
- **Способ оплаты** выбирает администратор: QR-код, перевод по номеру телефона или оба; реквизиты общие для всех мероприятий.
- **ФИО используются для идентификации платежа**: участник указывает их в сообщении к платежу.
- Кнопка «Открыть Сбербанк» показывается, только если в настройках задана ссылка; QR остаётся всегда.
- **QR сообщества и QR оплаты — разные настройки.** Рядом с QR Telegram-сообщества — кнопки Telegram, VK и MAX (миграция `005`); каждая показывается, только если задана её ссылка.
- **Оплата доступна только после регистрации:** ссылка `/payment/[publicId]` содержит случайный UUID регистрации, без ФИО и суммы.
- **Hero-фото, название, дата, время и описание** мероприятия редактируются в админпанели.

## Пока не реализовано

- реальная оплата, интеграция со Сбербанком и отметка факта оплаты;
- копирование архивов резервных копий за пределы сервера (off-site);
- несколько администраторов и роли (не планируются на текущем этапе);
- юридические согласия на обработку персональных данных;
- реальное развёртывание: сервер, домен, DNS, HTTPS, reverse proxy, cron, внешний мониторинг;
- проверка Docker-образа на Linux (`scripts/docker-smoke.sh`) — на рабочей машине нет Docker.
