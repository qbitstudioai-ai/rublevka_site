# Архитектура

Одно приложение Next.js 16 (App Router, TypeScript), одна локальная база SQLite и папка загруженных файлов. Внешних сервисов нет.

```text
Браузер ──► Next.js (Node runtime)
              ├─ публичные страницы   / (список мероприятий), /event/[slug], /payment/[publicId]
              ├─ админпанель           /admin/**
              ├─ выдача файлов         /media/[file]
              ├─ server actions        регистрация, действия админки
              └─ lib/server/**         валидация, репозитории, uploads, сессия
                    ├─ SQLite (better-sqlite3, WAL)   DATABASE_PATH
                    └─ файлы изображений              UPLOADS_DIR
```

## Слои

| Слой | Где | Что делает |
|---|---|---|
| Маршруты и страницы | `app/` | Серверные компоненты читают данные, клиентские — отвечают за интерактив |
| Server actions | `app/event/[slug]/actions.ts`, `app/admin/actions.ts` | Единственные точки изменения данных |
| Валидация | `lib/server/validation.ts` (zod) | Все входные данные считаются недоверенными |
| Репозитории | `lib/server/repo/*.ts` | SQL только через prepared statements; транзакции |
| Модели публичных страниц | `lib/server/public-data.ts`, `lib/types.ts` | Преобразование строк БД в данные для UI |
| Файлы | `lib/server/uploads.ts`, `app/media/[file]/route.ts` | Проверка, оптимизация, хранение и выдача изображений |
| Telegram | `lib/server/telegram.mjs`, `lib/server/telegram-outbox.mjs` | Текст уведомления без персональных данных (мероприятие + ссылка в админку), отправка через Bot API, durable outbox |
| Эксплуатация | `db/backup.mjs`, `lib/server/health.mjs`, `lib/server/env-check.mjs`, `instrumentation*.ts` | Бэкап, health, проверка env, закрытие БД при остановке |
| CLI | `scripts/*.mjs` | `db:migrate`, `db:seed`, `telegram:retry`, `backup` — чистый Node.js, работают в Docker без TypeScript |
| Excel | `lib/server/excel.ts`, `app/admin/(panel)/events/[id]/export/route.ts` | Генерация `.xlsx` в памяти для администратора |
| Сессия | `lib/server/session.ts`, `lib/server/admin-auth.ts` | Подписанная cookie единственного администратора |
| Миграции и seed | `db/`, `scripts/` | Управляемая схема и демо-данные |

Репозитории, валидация, uploads и сессия не зависят от Next.js — поэтому они проверяются интеграционными тестами на временной БД.

## Поток данных регистрации

```text
Анкета (клиент) ──► registerParticipant(slug, {ФИО, телефон, мессенджер, activityIds})
   1. zod-валидация данных участника
   2. мероприятие опубликовано? (в транзакции: и дата не раньше сегодняшней — иначе «Регистрация закрыта»)
   3. транзакция:
        услуги берутся из БД: принадлежат мероприятию и активны
        итог = стоимость участия (events.price_kopecks, обязательна) + фиксированные цены выбранных услуг
        (клиент сумму не передаёт; стоимость участия сохраняется в registrations.event_price_kopecks)
        INSERT registrations + snapshots в registration_activities
      + pending-запись telegram_notification_outbox (если Telegram настроен) — в той же транзакции
   4. after(): быстрая попытка отправки из outbox (после ответа пользователю);
      при неудаче запись остаётся pending — повтор через telegram:retry или админку
   5. ответ: publicId, название, ФИО, контакты, услуги, итог
Success-state ──► (если итог > 0) /payment/[publicId]
Страница оплаты читает регистрацию и snapshots из БД
```

## Разделение публичной части и админки

- Публично доступны только мероприятия со статусом `published`; черновики и архив отдают 404.
- Прошедшее мероприятие (дата раньше сегодняшней по времени комплекса, `isPastEvent`) открывается по ссылке, но вместо анкеты показывает «Регистрация закрыта». Сервер отклоняет регистрацию на него внутри транзакции (`createRegistration(..., { today })`, код `event_closed`), поэтому не помогает и открытая заранее вкладка. Страница оплаты уже сделанных регистраций продолжает работать.
- Главная `/` — список опубликованных мероприятий с датой не раньше сегодняшней (по времени комплекса), ближайшие первыми (`listUpcomingPublishedEvents`). Страница читает БД на каждый запрос, поэтому публикация, архив и удаление в админке видны сразу, без кэша и ревалидации.
- `/admin/**` (кроме `/admin/login`) требует сессию. Проверка выполняется в layout, в каждой странице и в каждом server action: проверка только в layout не защищает прямые POST-запросы.
- Админка и страница оплаты помечены `noindex`.
- Страницы, читающие БД, вызывают `connection()` или `cookies()`, поэтому никогда не попадают в статическую сборку.

## Telegram-уведомления

- Отправка напрямую в Telegram Bot API (`sendMessage`), без внешних сервисов. Настройка — `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` (см. `TELEGRAM.md`).
- **Durable outbox:** запись `telegram_notification_outbox` создаётся в транзакции регистрации, поэтому уведомление не теряется при остановке процесса. Сразу после ответа пользователю (`after()`) делается быстрая попытка.
- **Статусы:** `pending` → `sent`; после неудачи запись остаётся `pending` (attempts + 1), после 5 неудач — `failed`. `failed` повторяется только вручную (кнопка в админке, `telegram:retry -- --include-failed`).
- **Без дублей:** запись захватывается атомарным `UPDATE … locked_until`; отправленные (`sent`) не выбираются. Если процесс остановился во время отправки, захват истекает через 2 минуты — доставка «хотя бы один раз».
- Таймаут запроса — 10 секунд. В `last_error` и лог пишется краткая причина без токена.
- `fetch` передаётся зависимостью, поэтому автотесты не обращаются к настоящему Telegram (интеграционные — подменённый `fetch`, e2e — локальный mock Bot API через `TELEGRAM_API_BASE`).

## Excel-выгрузка

- `GET /admin/events/[id]/export` — route handler, сам проверяет сессию администратора (layout админки на route handlers не распространяется); без сессии — перенаправление на вход.
- Файл строится в памяти библиотекой `exceljs` и на сервере не сохраняется. Имя — `<slug>_uchastniki_<дата>.xlsx` только из проверенных значений.
- Выгружаются все регистрации мероприятия независимо от поиска в админке.
- Вторая колонка — «Название мероприятия»: текущее название из `events` (snapshot названия мероприятия в регистрации не хранится), чтобы выгрузки разных мероприятий можно было объединять.

## Эксплуатация

- **Health:** `GET /api/health` — SQLite (read-only, без создания файла), миграции, каталог uploads; `200 ok` / `503 degraded`, без путей и текстов ошибок.
- **Проверка env:** `instrumentation.ts` при запуске сервера проверяет обязательные переменные, пару Telegram, https в `APP_URL`, пути вне каталогов сборки; в production ошибки останавливают запуск.
- **Остановка:** Next.js обрабатывает SIGTERM и вызывает `process.exit`; обработчик `exit` закрывает SQLite (сброс WAL).
- **Бэкап:** `npm run backup` — см. `BACKUP.md`; восстановление — `RESTORE.md`.
- **Сборка:** `output: "standalone"` + `scripts/prepare-standalone.mjs` (полный `sharp`, статика, миграции; удаление случайно захваченных данных). E2E-тесты запускают именно `.next/standalone/server.js` в production-режиме.
- **Docker:** см. `DEPLOYMENT.md`.

## Загруженные файлы

- Хранятся в `UPLOADS_DIR` (по умолчанию `data/uploads/`), не в Git и не в `public/`.
- В БД записывается ссылка `upload:<uuid>.<webp|png>`. Также допускаются статические `/путь` (демо-QR из `public/mock`) и `https://` (демо-фото из seed).
- Отдаются маршрутом `/media/[file]`: имя проверяется строгим шаблоном UUID, выйти за пределы каталога нельзя.
- Порядок операций: новый файл сохраняется → транзакция БД → после commit удаляются файлы, на которые больше нет ссылок. Если транзакция не удалась, удаляются только что сохранённые файлы.

## Окружение

См. `.env.example`: `DATABASE_PATH`, `UPLOADS_DIR`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `ADMIN_SESSION_SECRET`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, необязательные `APP_URL` и `ADMIN_COOKIE_SECURE`. `TELEGRAM_API_BASE` используется только автотестами.

## Ограничения текущей архитектуры

- Один процесс приложения: ограничение частоты запросов хранится в памяти, SQLite — локальный файл.
- Доставка Telegram «хотя бы один раз»: при остановке процесса во время отправки возможен повтор сообщения.
- Реальной оплаты нет: QR и ссылка ведут в банковское приложение, сервис не знает о факте оплаты.
